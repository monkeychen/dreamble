# content-ops · 「聊哉梦呓」内容运营数据

本目录存放「聊哉梦呓」内容业务的**运行状态数据**：选题流水、发布复盘、数据基线、阶段目标。

## 为什么和 `skills/` 分开

`skills/` 存的是**方法论**——定位、评估体系、写作规范、审校清单。方法论应该稳定，改它意味着"改进做法"，需要 deliberate 的决策。

本目录存的是**业务流水**——每篇文章的复盘、每周的选题记录、每月刷新的基线。这些数据天然高频变化，改它只是"记账"，不涉及方法论变更。

**判据：更新这个文件，是在改进方法论，还是在记业务流水？**

| | 方法论（`skills/`） | 业务流水（`content-ops/`） |
|---|---|---|
| 更新频率 | 季度级，需 deliberate 决策 | 每篇 / 每周 / 每月 |
| 更新含义 | "我们的做法变了" | "又发生了一件事" |
| 过期后果 | 选题跑偏、文风漂移 | 只是数字旧了 |
| 例子 | 五条内容线的定义 | 某篇文章的阅读量 |

混在一起的后果：skill 变成一份需要频繁改动的文件，失去"稳定契约"的作用；而业务数据被埋在方法论里，既难追加也难归档。

## 目录结构

```
content-ops/
├── README.md              # 本文件：目录约定
├── baseline.md            # 数据基线快照（月度刷新，只留最新一份）
├── goals/                 # 阶段目标（一个周期一份，过期归档不删）
│   └── 2026Q4.md
├── topic-log.md           # 选题库流水账（持续追加，唯一真源）
└── reviews/               # 单篇复盘（发布后 7 天内填，一篇一份）
    └── 2026-10-XX-<slug>.md
```

## 文件职责与命名

| 文件 | 职责 | 命名 | 更新时机 |
|---|---|---|---|
| `baseline.md` | 内容产出、开源项目、渠道数据的**当前快照** | 固定名 | 每月初刷新，覆盖旧值，旧值移入 goals 当期文件 |
| `goals/<周期>.md` | 该周期的目标值、推导依据、进度 | `2026Q4.md`、`2027Q1.md` | 周期开始时建档，周期内更新进度，结束后封存 |
| `topic-log.md` | 所有候选选题（含被筛掉的）+ 筛选理由 | 固定名，表内按日期倒序 | 每次选题规划后追加 |
| `reviews/<日期>-<slug>.md` | 单篇文章的完整复盘 | 与 `site/content/posts/` 的目录名一致 | 发布后 7 天内 |

## 清理规则

- `baseline.md` **只保留最新快照**，不留历史版本（历史值在当期 goals 文件里）
- `goals/` **永久保留**，过期文件不删——它们是"当时怎么想的"的唯一证据
- `topic-log.md` 超过 200 行时，把已完结的旧记录剪到 `topic-log-archive-<年份>.md`
- `reviews/` **永久保留**，这是内容资产，不是临时产物

## 与 skills 的关系

`skills/topic-selector/` 定义**怎么做**（选题评估五维、热点过滤器、内容线比例），本目录记录**做了什么、结果如何**。

skill 的方法论文件里不写具体数字。需要现状数据时，skill 指向本目录：

- 选题规划 → 读 `topic-log.md` 看历史筛选记录，避免重复选题
- 月度复盘 → 读 `baseline.md` + 当期 `goals/` + `reviews/`
- 目标推导 → 读 `baseline.md` 的历史产能，**从数据推导，不从意愿推导**

## 数据纪律

1. **所有数字标出处和查询日期。** 查不到就写"待补"，不编造。
2. **实查优于记忆。** star、下载量、阅读量当场查 API 或后台，不用上次的数字。
3. **估算标明估算。** 按 0.7 token/字估出来的不能写成"实测"。
4. **样本 <5 不下结论。** 标"样本太少，不能判断"，不改策略。
5. **不美化。** 断更、失败、低于预期的周期如实记录——这些是最有信息量的数据。
