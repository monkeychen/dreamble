# 「聊哉梦呓」素材搜集系统

## 定位与原则

本系统服务于选题确定之后、正文撰写之前的素材准备环节。目标是为每篇文章搭建一个"素材弹药库"，让写作时有料可用、有据可引。

### 本号的素材优先级与大多数号相反

普通内容号：**外部权威素材优先**（找数据、找引言、找案例来支撑观点）。

本号：**一手素材优先**（自己的代码、日志、报错、实测数据、决策过程）。外部素材是补充，不是主体。

原因很简单：定位的核心是"真做出来了"。**别人能抄走你的结论，抄不走你的排查记录。**
一篇全靠外部素材的技术文，独家性评分天然上不去（见 topic-selector 的评估体系）。

搜集素材时先问一句：**这篇的一手材料够不够撑起主论证？** 不够就先去补一手材料（跑实验、翻日志、读源码），而不是去找更多外部素材来填。

### 三条铁律

1. **事实先行，观点在后。** 所有素材必须经得起查证。数据要有出处，报错要有原文，代码要能跑通，版本要标明。宁可少一个素材，不可用一个假素材。
2. **信息增量优先。** 读者随手能搜到的东西不叫素材，叫常识。官方文档里明写的用法不是素材，**文档没写而你实测出来的行为**才是素材。
3. **服务于观点。** 素材不是堆砌展示博学，每一条都要回答：它帮助论证了文章的什么观点？放不进逻辑链的素材，再精彩也要割舍。

### 第四条（技术文专属）：可复现性

凡是写"我实测的结果"，必须交代**环境**：操作系统、软件版本、硬件配置、时间。
不写环境的实测数据，读者复现不出来，就变成了不可验证的断言——这和编造数据只差一步。

## 素材的六种类型

### 类型1：一手代码与配置 ★ 独家性最高

自己写的代码、配置文件、diff、命令。这是本号最硬的素材。

质量标准：
- **只保留能说明问题的片段**，不要整段粘贴。超过 15 行考虑折叠成要点
- 标明来源文件和行号（读者想深挖时找得到）
- 如果是"错误写法"，明确标注这是反面示例，并给出正确写法
- 敏感信息必须清理：token、密码、内网 IP、私有仓库地址、企业系统名

好的代码素材示例：
> 内核判断目录是否可写用的是 `stat` 而不是 `lstat`——一个字的差别，决定了软链能不能被跟随：
> ```js
> const isDirectoryEntry = (p) => fs.statSync(p).isDirectory()
> ```
> 换成 `lstat`，我这套软链方案当场失效。

### 类型2：实测数据与基准 ★ 独家性最高

自己跑出来的数字：耗时、token 消耗、内存占用、下载量、成功率、成本。

质量标准：
- **必须带环境**：机器配置、软件版本、测试时间、样本量
- 标明测量方法（跑了几次、取平均还是取最好一次、有没有剔除异常值）
- 有对比基准（跟什么比？旧版本？官方宣称值？手动操作？）
- 概数要明说是概数（"约 11.7k tokens"而不是"11700 tokens"）

注意事项：
- **单次测量不要写成规律**。跑一次的结果标"单次实测"，跑三次以上才能说"通常"
- 样本 <5 的统计结论，明确标注"样本太少，不能判断"
- 性能数据受环境影响极大，务必写清环境，否则读者复现不出会认为你在吹

好的实测数据示例：
> 当前 47 个 skill 的 description 加起来约 11.7k tokens（中文按 0.7 token/字估算），而这个数字**每一轮请求都要付一次**。测量环境：WorkBuddy CLI，2026-08-30。

### 类型3：报错、日志与错误码

原始报错信息、日志片段、平台返回码。技术文的"案发现场证据"。

质量标准：
- **保留原文**（读者要拿它去搜，翻译过的搜不到）
- 紧跟一句人话翻译：这个报错实际在说什么
- 标明触发条件（什么操作、什么版本下出现的）
- 如果是平台错误码，记录官方文档怎么说、**实际行为是什么**（两者常不一致，这个差值就是素材）

好的报错素材示例：
> ```
> errcode 45166, errmsg invalid content hint
> ```
> 官方文档对这个码只有一句话：内容不合规。不告诉你是哪一句，也不告诉你是哪一层判断。我试了三轮才摸清它是两层过滤。

### 类型4：决策记录 ★ 技术文最缺、最值钱

方案对比、取舍理由、被排除的选项、付出的代价。**别人能抄走结论，抄不走取舍过程。**

质量标准：
- 写清**当时有哪几个选项**（至少 2 个，只写最终选择的等于没写）
- 每个选项的真实成本：时间、复杂度、可维护性、用户体验、依赖风险
- 排除某个选项的**具体依据**（实测数据、平台限制、维护负担），不要写"感觉不好"
- **必须写代价**：这个决定让你放弃了什么，有没有留下后遗症
- 记录决策时间（三个月后回头看，判断依据可能已经变了）

好的决策记录示例：
> 摆在面前三条路：继续逆向接口、换官方 API、用真实浏览器在协议层拦。第一条最省事，但对方每改一次前端我就得跟着修一次（过去一年已经修了 4 次）。第二条要企业资质，我一个人拿不到。第三条最笨——启动一个浏览器，慢、占内存。我选了最笨的那条，因为它不会因为对方改前端而失效。代价是启动时间从 200ms 变成 3s。

素材来源：git commit message、issue/PR 讨论、项目里的 AGENTS.md/README 变更记录、`.workbuddy/memory/` 的工作日志。**这些地方存着大量现成的决策记录，写文章前先翻一遍。**

### 类型5：外部依据（文档、规范、他人讨论）

官方文档、协议规范、源码注释、issue/PR 讨论、权威技术分析。用于佐证或对比。

质量标准：
- **标明版本和访问日期**（文档会变，链接会失效，写清"截至 2026-10 的文档"）
- 优先一手来源：官方文档 > 源码 > 维护者的 issue 回复 > 社区讨论 > 二手博客
- 引用他人观点必须给出处，**不要把自己的推测写成"业界普遍认为"**
- 文档与实际行为不一致时，两边都记下来——**这个不一致本身就是最好的素材**

注意事项：
- AI 搜索到的技术细节需要交叉验证，尤其是版本号、API 签名、配置项名称
- 找到文档没覆盖的行为，标注"文档未说明，以下为实测"
- 不要用过期教程。技术类内容的半衰期短，一年前的教程可能已经全错

### 类型6：类比与隐喻

用其他领域的事物解释抽象的技术概念。这是「聊哉梦呓」文风的重要组成部分。

质量标准：
- 映射关系准确（A 的哪个特征对应 B 的哪个特征）
- 来源是读者熟悉的领域（日常生活、排队、交通、建筑、水管、做饭、医学）
- 要揭示本质，而非仅仅"像"
- 一篇不超过 2-3 个，多了会散
- **类比之后必须拉回来**，用一句话点明"所以这跟我们讨论的 XX 有什么关系"

好的类比示例：
- "sshd 配置的首值优先，就像排队——先来的人先被听见，后面喊得再大声也没用。"
- "逆向别人的接口，和照着钥匙的磨损痕迹配钥匙是一回事：门一换，钥匙就废了。"
- "skill 注册表是会话启动快照，跟你改完配置文件不重启服务是一个道理。"

坏的类比：过度延伸的比喻，比喻了半段还在比喻，读者已经忘了你在说什么。

## 素材搜集工作流

### 步骤1：明确搜集方向

从用户给出的选题/提纲中，提取需要素材支撑的关键论点。每个论点对应一个"素材需求"。

操作方法：
- 列出文章的 3-5 个核心论点
- **先盘一手素材**：这个论点我有代码/日志/实测数据/决策记录吗？在哪？（git log、项目目录、memory 日志、聊天记录）
- 再标注缺口：哪些论点缺一手支撑，需要补做实验或翻源码
- 最后才补外部素材：哪些地方需要官方文档或他人分析来佐证
- 判断哪些素材必须有（文章骨架），哪些锦上添花（调味料）

> ⚠️ 如果发现某个核心论点**完全没有一手素材**，先告诉用户："这块你没亲手做过，
> 要么现在去跑一遍，要么这个论点降级为背景说明，不能作为主论证。"
> 不要用外部素材伪装成一手经验——这是本号的信任底线。

### 步骤2：分层搜索

**第一层：核心素材（必须有）**
- 支撑核心观点的代码、报错、实测数据、决策记录
- 没有这些素材，文章立不住

搜索策略：先翻本地（项目目录、git log、memory 日志），再翻线上（issue、PR、官方文档）

**第二层：增强素材（应该有）**
- 让论证更丰满的对比数据、失败案例、他人踩坑记录
- 没有它们文章能成立，但会单薄

搜索策略：搜同类问题的 issue 讨论、社区复盘、官方 changelog

**第三层：点睛素材（最好有）**
- 让文章出彩的金句、巧妙类比、冷知识、反直觉事实
- 这是文章从"合格"到"优秀"的差距

搜索策略：跨领域联想、翻源码里的注释和 commit message（常有意外收获）

### 步骤3：素材验证

对搜集到的每条素材做以下检查：

- **准确性**：代码能跑吗？数字对吗？报错原文对吗？版本号对吗？
- **时效性**：这是最新版本的行为吗？文档有没有更新？依赖有没有换实现？
- **可复现性**：环境交代清楚了吗？读者照着做能得到同样结果吗？
- **完整性**：因果链条完整吗？有没有只留对自己有利的部分？
- **合规性**：有没有泄露 token、密码、内网信息、企业数据、未公开架构？

对于无法 100% 确认的素材，统一标注 ⚠️ 待核实，并说明存疑之处。

**技术类素材特有的验证动作**：
- 命令**实际跑一遍**再写进文章（不跑就是编）
- 报错**保留原始输出**，不要凭记忆复述
- 引用文档**核对版本**，注明访问日期
- 性能数据**至少跑三次**，说明取值方法

### 步骤4：素材组织与输出

搜集完成后，按结构化格式整理输出（见下方输出格式）。

## 按内容线的素材搜集重点

### 造物记（产品设计决策与踩坑）
- **核心需求**：决策记录（方案对比 + 代价）、被砍功能的原始实现、git commit 里的演进痕迹
- **辅助需求**：用户 issue 反馈、下载/star 数据、同类产品的做法对比
- **搜索重点**：自己项目的 git log、issue 区、README 变更记录、`.workbuddy/memory/` 日志
- **常用搜索词**：`git log --grep="关键词"`、项目 issue 关键词、同类工具的设计取舍

### 拆机间（读源码、拆机制）
- **核心需求**：源码片段（关键函数）、文档原文与实际行为的差异、机制的边界条件
- **辅助需求**：相关的 issue/PR 讨论、维护者的解释、历史版本的实现变化
- **搜索重点**：源码仓库、官方文档、issue 区搜"not working""unexpected"
- **常用搜索词**：`<项目名> <机制> source`、`<项目名> issue <行为>`、文档里的关键词精确匹配

### 流水线（自动化链路）
- **核心需求**：完整链路的各环节实现、最脆弱一环的失败案例、时间/成本账
- **辅助需求**：搭建过程的工作日志、返工记录、依赖变更导致的断链
- **搜索重点**：项目脚本、CI 配置、memory 日志里的踩坑记录
- **常用搜索词**：链路中每个工具的限制、集成失败的报错

### 事故现场（故障归因）
- **核心需求**：原始报错与日志、排查过程中的**错误假设**、真凶所在的那一行、修复后的验证
- **辅助需求**：同类事故的他人复盘、官方对这类问题的说明、监控数据
- **搜索重点**：系统日志、当时的终端记录、memory 日志（**事故发生时记的最准，过后细节就忘了**）
- **常用搜索词**：报错原文（去掉变量部分）、错误码、`<软件> <现象> root cause`

### 框架与判断（辅线，无个股）
- **核心需求**：自己实践中的数据支撑、真实失败案例、判断框架的应用实例
- **辅助需求**：可复用的方法论、他人验证过的框架、反例
- **搜索重点**：自己的项目数据、工程决策记录
- ⚠️ **严禁**：个股名称、买卖评级、目标价、点位预测（公众号会返 45166 拒稿）

## 搜索策略指南

### 基本搜索原则
- **先本地后线上**：一手素材大多在自己的项目目录、git log、memory 日志里，先翻这些
- 先广后窄：先用宽泛关键词了解全貌，再用精确词挖掘细节
- 中英双语：技术类问题的英文资料通常更丰富、更准确、更新更快
- 多源交叉：同一个事实至少查两个独立来源
- **原始优先**：源码 > 官方文档 > 维护者回复 > issue 讨论 > 社区博客 > 二手教程

### 本地素材的挖掘方法（本号最重要的搜索技能）
- `git log --grep="关键词"` / `git log -p <文件>`：找决策演进痕迹，commit message 里常有现成的取舍理由
- `.workbuddy/memory/YYYY-MM-DD.md`：工作日志，**事故和踩坑记录最全的地方**
- 项目里的 `AGENTS.md` / `README.md` 变更记录：规则为什么这么定，通常写在里面
- issue 区搜自己的项目：用户反馈是最真实的"代价"证据
- 翻依赖库的源码和注释：注释里常有文档没写的坑

### 搜索组合技巧
- **报错原文精确搜**：去掉变量部分（路径、ID、时间戳）后加引号搜
- **错误码 + 项目名**：`errcode 45166 公众号`
- **现象 + root cause**：`<软件> <现象> root cause`
- **版本限定**：搜索时带上版本号，避免拿到旧版本的解法
- **反向搜索**：搜"XX 为什么不用 YY"，常能找到他人的决策记录

### 素材不足时的应急策略
如果核心素材搜索困难，可以：
1. **自己跑一遍**——最有效的办法。技术文的一手素材是"做"出来的，不是"搜"出来的
2. 更换切入角度——可能某个角度更容易找到支撑素材
3. 降维使用——用一个小案例代替宏大叙事
4. 坦率标注——告知用户此处需要补充素材，建议查阅或实测的方向
5. 反向思维——找不到正面案例，找反面案例（失败记录）也能论证，而且往往更有说服力

> ❌ **不允许的做法**：用外部素材伪装成自己的实测结果。
> 拿不到一手材料就明说"这块我没验证过"，这符合 style-dna 的谦逊阀门要求。

## 额外提示

- 素材搜集环节应主动使用搜索工具获取最新、最准确的信息，而非仅依赖模型内置知识。**技术类知识的过期速度极快，模型内置知识大概率是旧版本的。**
- 对于版本号、API 签名、配置项名称、命令参数，务必实际验证。AI 在这些细节上出错率最高，且错得很像真的。
- 素材包不是越多越好。一篇 2000-3500 字的文章，核心素材 3-5 条 + 增强素材 2-3 条 + 点睛素材 1-2 条就足够了。素材过多反而会让文章失焦。
- **代码块数量控制在 3-5 个**。技术文最容易犯的错是变成代码 dumps——读者要的是判断，不是仓库镜像。
- 如果用户已经有了文章提纲，素材搜集应严格按照提纲结构来组织，确保每个段落都有对应的素材支撑。
- 搜集过程中发现某条素材很精彩但与当前选题关联不大，单独标注为"素材备忘"，建议存入 [topic-library.md](../topic-selector/references/topic-library.md) 留待未来使用。
- **事故发生时立刻记录**。排查过程的细节（尤其是错误假设）过一周就忘了，而那恰恰是事故现场类文章最有价值的部分。
