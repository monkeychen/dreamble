# 素材事实核查指南

> 本文件提供素材核查的具体方法和技术写作中常见的事实错误类型。
> 每条素材入库前都应过一遍本指南中的检查清单。

---

## 核查的基本原则

**宁可不用，不可用错。** 一个错误的版本号或凭记忆复述的报错，会摧毁整篇文章的公信力。技术类读者尤其会去复现——复现不出来，你后面说的所有话他都不信了。

**标注不确定性。** 如果无法 100% 确认某条素材的准确性，不要假装确定。在素材包中标注 ⚠️ 待核实，并建议用户自行验证后再使用。

**技术文的额外底线：可复现。** 凡是写"我实测的结果"，必须交代环境（系统、版本、硬件、时间、样本量）。没有环境的实测数据等于不可验证的断言，和编造只差一步。

**跑一遍再写。** 命令、代码、配置在写进文章前**实际执行一次**。不跑就是编。

## 分类核查清单

### 一、实测数据核查

| 核查项 | 具体操作 |
|-------|---------|
| 环境是否交代 | 操作系统、软件版本、硬件配置、测试时间 |
| 样本量是否足够 | 跑了几次？单次结果不能写成规律 |
| 取值方法是否说明 | 平均 / 最好一次 / 中位数？有没有剔除异常值 |
| 对比基准是否明确 | 跟什么比？旧版本？官方宣称值？手动操作？ |
| 单位是否正确 | ms vs s、MB vs MiB、token vs 字符、次/月 vs 次/日 |
| 数字是否可复现 | 读者照你的环境和步骤做，能得到接近的数吗 |
| 是否最新 | 版本更新后数据可能全变，标明测量时的版本 |

**常见实测数据错误：**
- 跑一次就写"通常耗时 X 秒"（样本量为 1 不能得出"通常"）
- 混淆 ms 和 s、MB 和 MiB（差 4.8%~1000 倍）
- 混淆 token 数和字符数（中文约 0.7 token/字，估算要说明）
- 只报最好的一次，不说明剔除了多少次失败
- 换了机器/版本后沿用旧数据，未标注测量环境
- 把"下载量"和"安装量"混为一谈（口径不同）
- GitHub star 当成使用量（star 是虚荣指标，issue 数才说明真在用）

### 二、代码与命令核查

| 核查项 | 具体操作 |
|-------|---------|
| 是否实际跑过 | **没跑过的代码不许进文章** |
| 版本号是否标注 | 这段代码在哪个版本下有效 |
| 依赖是否说明 | 需要装什么、什么版本、有没有隐含前提 |
| 敏感信息是否清理 | token、密码、内网 IP、私有仓库地址、企业系统名 |
| 是否为最小片段 | 只留能说明问题的部分，不要整文件粘贴 |
| 反面示例是否标注 | 如果是"错误写法"，明确标出来，并给正确写法 |
| 路径是否硬编码 | `/Users/xxx/` 这类私人路径要换成占位符 |

**常见代码类错误：**
- 凭记忆写命令，参数名或顺序错了（**最容易犯，且看起来很像真的**）
- 把旧版本的 API 写进新版本的文章
- 省略了必要的前置步骤，读者照着跑直接报错
- 代码块里留着真实的 token 或密码（**发布前必须逐行扫一遍**）
- 引用了 `node_modules` 里的代码但没标明包名和版本
- 把"我的环境里能跑"当成"通用解法"（依赖、权限、平台差异）
- macOS / Linux / Windows 的命令差异未说明（如 macOS 无 `timeout` 命令、BSD grep 不认 `\|`）

### 三、报错与日志核查

| 核查项 | 具体操作 |
|-------|---------|
| 是否原文保留 | 报错要原样贴，读者要拿它去搜 |
| 是否凭记忆复述 | **不许**。回去翻日志或重新触发一次 |
| 触发条件是否记录 | 什么操作、什么版本、什么环境下出现 |
| 变量部分是否说明 | 报错里的路径/ID/时间戳是变量，搜的时候要去掉 |
| 是否有后续修复 | 只报错不给解法，等于半个素材 |
| 平台错误码是否查过官方 | 官方解释 + 实际行为，两边都记 |

**常见报错类错误：**
- 凭印象编一个"看起来像"的报错（技术读者一眼看穿）
- 只贴最后一行，丢了真正的根因（堆栈顶部往往不是问题所在）
- 报错和解法不是同一次事件（拼凑痕迹明显）
- 把偶发问题写成必现（没说明触发概率）
- 官方文档对错误码的解释过于简略，误以为"就这个原因"
  （如 errcode 45166 官方只说"内容不合规"，实际是两层过滤）

### 四、文档与技术断言核查

| 核查项 | 具体操作 |
|-------|---------|
| 文档版本 | 看的是哪个版本的文档，是否匹配你的实际版本 |
| 访问日期 | 文档会变，链接会失效，写清"截至 YYYY-MM" |
| 文档与实际是否一致 | **不一致时两边都记，这个差值就是素材** |
| 来源层级 | 源码 > 官方文档 > 维护者回复 > issue 讨论 > 博客 > 二手教程 |
| 是否过期 | 技术内容半衰期短，一年前的教程可能全错 |
| 二手转述是否核对原文 | 很多"官方说"其实是某篇博客说的 |

**常见文档类错误：**
- 引用了已废弃（deprecated）的 API 或配置项
- 把社区博客的说法当成官方结论
- 文档滞后于实现（文档说支持，实测不支持，或反之）
- 混淆了同名工具的不同版本/不同分支
- 把"某个版本的行为"写成"这个工具的行为"
- 断言"不支持"但只查了文档没读源码（文档没写 ≠ 不支持）
- 模型内置知识当成现状（**AI 对技术细节的记忆大概率是旧版本的**）

### 五、决策记录核查

| 核查项 | 具体操作 |
|-------|---------|
| 方案是否完整 | 当时真有几个选项？只写最终选择等于没写 |
| 排除依据是否具体 | "感觉不好"不算依据，要有实测数据/平台限制/维护成本 |
| 代价是否写了 | 放弃了什么，有没有后遗症 |
| 时间线是否准确 | 什么时候决策的，之后有没有推翻 |
| 是否美化了过程 | **误判和弯路如实写**，那是文章最有价值的部分 |
| 是否有据可查 | git commit、issue、memory 日志里能不能找到对应记录 |

**常见决策记录错误：**
- 事后合理化：把"当时随便选的"写成"经过深思熟虑"
- 只写成功路径，删掉试错的三步（读者最需要的恰恰是那三步）
- 代价一笔带过或完全不提（变成软文）
- 把别人的决策写成自己的
- 时间线错乱（先有的 A 还是先有的 B，影响因果叙述）

## AI 生成素材的特别注意事项

AI 在搜集技术素材时有几类系统性风险，需要特别警惕：

### 容易出错的领域（按错误率排序）
1. **命令参数与 API 签名**：AI 会编造"看起来对"的参数名、flag、方法签名
2. **版本号**：AI 常给出过时或不存在的版本号
3. **具体数字**：性能数据、下载量、star 数——**必须实查，不许用记忆值**
4. **配置项名称**：拼错一个字母，或用了别的软件的配置名
5. **报错原文**：AI 会生成"像那个报错"的文本，但不是原文
6. **文件路径与目录结构**：AI 会按惯例猜路径，实际项目可能完全不同
7. **因果关系**：AI 会把"先后发生"写成"因此导致"
8. **"业界普遍认为"**：AI 爱用这个短语，但它往往没有依据

### 应对策略
- **命令和代码：实际执行一次**。跑不通就不写，或标注"未验证"
- **数字：当场查 API 或后台**，并在素材包里记录查询时间
- **报错：回原始日志复制**，不许复述
- **文档：核对版本号 + 记录访问日期**
- **源码断言：给出文件路径和行号**，让用户能自己去看
- 搜索结果如果来自低质量来源（论坛、自媒体），进一步查证一手来源
- 对无法验证的素材统一标注 ⚠️，交给用户最终把关
- **宁可输出"未找到可靠依据"也不编造**
- 拿不到一手材料时，明确写"这块我没验证过"——符合 style-dna 的谦逊阀门要求

### 本号特有的核查项：合规
- **敏感信息**：token、密码、AppSecret、内网 IP、服务器公网 IP、私有仓库地址
- **企业信息**：未公开的架构、业务数据、客户名称、内部系统名、产品规划
- **平台红线**：个股名称 + 买卖评级/目标价/点位 → **公众号必返 errcode 45166**，只能走站点
- **第三方内容**：大段引用文档或他人文章是否有合理使用问题；截图里有没有别人的隐私信息

## 快速核查流程

对每条素材做如下四步快速检查：

**第一步：来源检查**
→ 这条信息的原始来源是什么？是源码/官方文档，还是二手转述？

**第二步：交叉检查**
→ 能否从另一个独立来源找到相同的信息？（本地实测 × 线上文档 是最好的组合）

**第三步：复现检查**（技术素材专属）
→ 环境交代了吗？命令跑过了吗？读者照着做能得到同样结果吗？

**第四步：常识检查**
→ 这条信息是否符合基本逻辑？数量级是否合理？有没有把相关当因果？

四步都通过 → ✅ 标记为已核实
任一步有疑问 → ⚠️ 标记为待核实，注明存疑点

## 发布前的最后一道关

文章成稿后、发布前，对**全文**再扫一遍：

- [ ] 所有命令都实际跑过，且标注了适用版本/平台
- [ ] 所有数字都是当场查的，且标了查询日期或测量环境
- [ ] 所有报错都是原始输出，不是复述
- [ ] 所有代码块都扫过，无 token / 密码 / 内网 IP / 私人路径
- [ ] 所有文档引用都标了版本和访问日期
- [ ] 无个股名称 + 评级/目标价/点位（公众号渠道）
- [ ] 无未公开的企业架构、业务数据、客户名称
- [ ] 所有"我实测"的说法都真的一手，没有拿外部素材冒充
- [ ] 决策记录写了代价，不只写成功路径
- [ ] 误判和弯路如实保留，没有美化

**任一项不过，改完再发。**
