# 素材来源指南

> 本文件按素材类型分类，列出可信赖的信息来源和搜索渠道。
> 搜集素材时优先使用本文件推荐的来源，确保信息的权威性和准确性。
>
> **本号的一手素材优先级高于外部素材**——先挖本地（见第一章），再查线上。

---

## 一、本地一手素材源 ★ 最优先，独家性最高

外部素材谁都能搜到，本地素材只有你有。**每次搜集素材都从这里开始。**

### 项目目录
- **自己的代码仓库**：`apps/`（wx-kit、xtract、stockfunnel、x-reader）、`site/`、`skills/`
- **配置与规则文件**：各项目根目录的 `AGENTS.md` / `CLAUDE.md` / `GEMINI.md` / `README.md`
  —— 规则为什么这么定，取舍理由通常就写在里面
- **CI/部署脚本**：`.github/workflows/`、`scripts/`、`bin/`、`package.json` 的 scripts 段
  —— 流水线类文章的核心素材
- **文档目录**：`docs/`（如 `site/AGENTS.md`、`docs/deploy.md`、`docs/dreamble-site-vibe-coding.md`）

### 版本历史（决策记录的富矿）
- `git log --oneline` / `git log --grep="关键词"`：找某类改动的演进
- `git log -p <文件>`：看一个文件怎么变成现在这样的
- `git show <commit>`：某次决策的完整上下文
- **commit message 里常有现成的取舍理由**，直接就是"决策记录"类素材

### 工作日志
- `.workbuddy/memory/YYYY-MM-DD.md`：**事故和踩坑记录最全的地方**
- `.workbuddy/memory/MEMORY.md`：长期结论与已验证的事实
- 里面记的实测数据（token 成本、错误码、配置坑）都是可直接引用的一手素材

### 运行时证据
- 终端历史（`~/.zsh_history`）：当时到底跑了哪些命令
- 应用日志：`/var/log/`（服务器）、Electron 应用的 log 目录、CI 日志
- 浏览器 DevTools / Network 面板：平台接口的真实请求与响应
- 本地数据库 / 缓存文件：如 xtract 的 SQLite、`~/.bun/install/cache`

### 项目运营数据
- GitHub API：`api.github.com/repos/<owner>/<repo>`（star、fork、watcher、issue 数）
- Release 下载量：`api.github.com/repos/<owner>/<repo>/releases` 累加各 asset 的 `download_count`
- npm 下载量：`api.npmjs.org/downloads/point/last-month/<package>`
- 站点数据：GoAccess 面板（服务端日志聚合）、百度统计（搜索词、停留时长）
- 公众号后台：阅读、打开率、分享、在看、关注变化

> ⚠️ **这些数字必须实查，不要用记忆里的旧数字。** 写进文章前当场查一次，并记录查询日期。

## 二、代码与实现依据

### 源码
- **依赖库源码**：`node_modules/`、Python 的 site-packages、`~/.bun/install/cache`
  —— 文档没写的行为，源码里有答案。**这是拆机间类文章的核心素材**
- **打包产物**：Electron 的 `.asar.unpacked/`、`dist/`
  —— 商业软件没有开源时，读打包产物是唯一路径（如 WorkBuddy 的 `codebuddy.js`）
- **GitHub 上的开源项目**：搜具体函数名比搜问题描述更容易命中

### 官方文档与规范
- 各工具/框架的官方文档（**务必核对版本号**，文档常滞后于实现）
- 语言与协议规范：ECMA、RFC、W3C、POSIX
- API 参考：注意区分"文档说的"和"实际行为"，两者不一致时都是素材

### 变更历史
- 官方 Changelog / Release Notes：找某个行为是从哪个版本开始变的
- 项目的 CHANGELOG.md、迁移指南（migration guide）
- 废弃公告（deprecation notice）

## 三、报错与问题排查

### 一手来源（最可靠）
- **自己的终端输出和日志文件**：保留原文，不要凭记忆复述
- **平台返回的错误码 + errmsg**：连同触发条件一起记录
- **DevTools 的完整堆栈**：报错行号往往不是真凶所在

### 二手来源
- **GitHub Issues**：搜报错原文（去掉路径、ID、时间戳等变量部分），命中率最高
  - 优先看维护者的回复，其次看高赞评论
  - 注意 issue 的时间——老 issue 的解法可能已失效
- **Stack Overflow**：看投票最高的答案，**但一定核对答案的日期和适用版本**
- **官方论坛 / Discord / Slack**：维护者的答复比文档更及时
- **搜索引擎**：报错原文加引号精确搜，比描述现象有效得多

### 平台官方状态页
- GitHub Status、各云服务商的状态页、npm/PyPI 的可用性页面
- 排查前先确认不是平台侧故障，能省几小时冤枉路

## 四、技术趋势与行业动态

### 一手来源
- **项目官方博客与发布稿**：Anthropic、OpenAI、Google、Meta AI、各家开源项目
- **官方 GitHub 仓库的 Release 与 Roadmap**
- **论文**：arXiv（cs.CL / cs.LG / cs.SE）、各会议的 accepted papers
- **RFC 与标准草案**：协议层变化的最早信号

### 中文技术社区
- 各项目/厂商的官方中文文档与公众号
- 掘金、知乎的技术专栏（**质量参差，需交叉验证**）
- V2EX、少数派、阮一峰的网络日志（周刊类，适合了解概览）

### 英文技术媒体
- Hacker News（news.ycombinator.com）：看评论区，常有一线开发者的实测反馈
- Lobsters、Reddit 的相关 subreddit（r/programming、r/selfhosted 等）
- 各语言/框架的 Weekly 通讯

### 逆向与协议研究
- 相关项目的 issue 区（"为什么突然不能用了"往往最先出现在这里）
- 反编译/抓包记录（**自己抓的才可信**）

## 五、方法论与思维框架

### 经典著作（跨领域，非投资专属）
- 《人月神话》——布鲁克斯：软件工程的人力与复杂度
- 《编程珠玑》——本特利：性能与取舍
- 《重构》——福勒：代码演进的方法
- 《UNIX 编程艺术》——雷蒙德：设计哲学
- 《设计原本》——布鲁克斯：设计过程
- 《思考，快与慢》——卡尼曼：认知偏差（**跨界到工程决策时很有用**）
- 《"错误"的行为》——塞勒：行为经济学
- 《反脆弱》《黑天鹅》——塔勒布：不确定性
- 《系统之美》——梅多斯：系统思维
- 《清单革命》——葛文德：把隐性能力显性化

### 工程实践类
- Google SRE Book（在线免费）：可靠性、事故复盘、监控
- 《凤凰项目》《独角兽项目》：DevOps 小说体，适合类比取材
- 各公司的工程博客：GitHub Engineering、Cloudflare Blog、Netflix TechBlog、
  Google Research Blog —— **事故复盘和架构决策的高质量来源**

### 认知与决策
- 认知偏差清单（锚定、沉没成本、幸存者偏差、后视镜偏差）
  —— 用于「框架与判断」线，**但要结合自己的工程实例，不要空谈理论**
- 第一性原理、逆向思考（芒格的"反过来想"）
- 概率思维与贝叶斯更新

## 六、类比与隐喻的灵感来源

类比没有固定来源，但以下领域是高频取材区：

- **日常生活**：排队、做饭、装修、开车、看病（**最容易让读者秒懂**）
- **建筑与水管**：承重墙、管道堵塞、水压、地基（适合描述架构与依赖）
- **交通**：堵车、单行道、红绿灯、匝道（适合描述并发、限流、优先级）
- **医学**：诊断、用药、免疫、复健、退烧（适合描述故障排查与修复）
- **物理学**：惯性、摩擦力、临界点、杠杆、熵（适合描述技术债与系统劣化）
- **生物学**：进化、寄生、共生、生态位（适合描述依赖关系与竞争格局）
- **军事/体育**：补给线、阵地战、马拉松配速（适合描述长期项目推进）

使用原则：类比的本体和喻体之间的映射关系必须准确，不能只是"感觉像"。
类比之后必须拉回来，一句话点明"所以这跟我们讨论的 XX 有什么关系"。

**技术文的好类比通常来自"结构相同"而非"表面相似"**：
- ✅ "sshd 配置首值优先，就像排队——先来的人先被听见"（结构相同：先到先得，后者被忽略）
- ❌ "代码像诗一样优雅"（表面相似，没有解释力）

## 使用建议

1. **每次搜集都从第一章（本地一手素材）开始。** 先问"我手上有什么"，再问"外面有什么"。
   顺序反了，写出来的就是全网都有的那种技术文。
2. 搜索素材时先确定需要哪种类型，再到对应的来源区寻找，避免漫无目的地搜索。
3. 中文和英文来源交叉使用。**技术类问题英文资料通常更丰富、更准确、更新更快**，
   尤其是新版本特性和边缘 bug。
4. 对于任何"据说""有人说""网上流传"的内容，如果找不到可靠出处，不用。
5. **注意版本时效**：技术内容的半衰期短，一年前的教程可能已经全错。
   引用任何技术细节都标明版本号和访问日期。
6. 书籍类来源主要用于提供框架和思维模型，**具体的技术细节必须通过搜索或实测获取最新版本**。
7. **实查优于记忆**：所有数字（star、下载量、耗时、token）当场查，记录查询时间。
   模型内置的技术数据大概率是过期的。
