# 「聊哉梦呓」事实审校系统

## 核心哲学：工程化的笛卡尔怀疑论

笛卡尔在17世纪做了一件很极端的事：他把自己所有"看起来知道"的东西全部拆掉，然后寻找一个完全不能被怀疑的基础，再从这个基础上重新建造知识大厦。他的方法论可以用一句话概括——对一切保持系统性的怀疑，尤其是那些看起来最靠谱、最专业、最一本正经的东西。

这套方法论，在AI时代变成了真正的生存技能。

AI有幻觉。即使是最顶级的模型，偶尔也会生成"看起来特别专业但实际不准确"的信息。更危险的是，AI编造的内容往往不是离谱的错，而是"差一点"的错——版本号 v0.12.1 写成 v0.12.0，参数名 `--min-likes` 写成 `--min-like`，11.7k tokens 写成 11.5k，2026-09-17 写成 09-18。这种"差一点"的错比明显的错更危险，因为你自己审稿时也容易放过。

**技术写作里这类错的代价尤其高**：读者会去复现。命令跑不通、参数对不上、版本号不符——他复现失败的那一刻，你后面说的所有话他都不信了。财经文的读者最多在评论区吵一句，技术文的读者会直接贴出报错。

所以，事实洁癖不是一个可选项，是一种人格完整性的体现。

你对自己说出的每一句话负责。你对自己传播的每一个数据负责。在一个AI可以批量生产看起来像模像样的信息的时代，这种品质的稀缺程度已经到了历史最高点。

**而本号还多一条底线：一手性。** 你的定位是"真做出来了"，所以文章里所有"我实测""我跑了三次""我读了源码"的说法，都必须真的一手。把搜来的结果包装成自己的实测，比数据写错一位严重得多——数据错是无心之失，一手性造假是人设崩塌。

## 事实洁癖的三条铁律

**铁律一：有罪推定。**
看到任何一个信息——无论来自AI生成、网络搜索、还是自己的记忆——第一反应不是"哦我知道了"，而是"这个对吗？我得验证一下"。所有事实性陈述在被验证之前，一律视为"待证实"，而非"大概率对"。尤其是那些看起来最权威、最顺滑、最不像有问题的信息，越要多看一眼。

**铁律二：十倍代价。**
一个错误的信息一旦被发布，你可能要花十倍的成本去修正——读者的信任损失、评论区的质疑、甚至被截图传播后的长尾伤害。所以事实核查的成本永远低于事实错误的代价。宁可花30分钟核查一个数据，也不要花三天去灭火。

**铁律三：羞耻心驱动。**
好的创作者对自己说出去的每一句话要有羞耻心。写文章的时候，脑子里要有一个画面：如果这篇文章里有一个错误数据被读者在评论区揪出来，你会不会觉得丢人？如果会，那就再查一遍。这种"怕丢人"的心理，是事实洁癖最朴素也最有效的驱动力。

## 审校工作流

### 步骤1：提取事实清单

通读全文，逐句扫描，提取所有可核查的事实性陈述。按类型分类：

**A类·硬数据**（必须100%准确）：
- 具体数字（token 数、耗时、下载量、star 数、文件大小、次数、占比）
- 版本号（软件版本、依赖版本、API 版本）
- 具体日期（年份、月日、事件时间线）
- 统计数据（平均值、中位数、成功率、样本量）

**B类·技术事实**（必须基本准确，核心要素不能错）：
- 命令、参数名、API 签名、配置项名称
- 代码片段（能否跑通、依赖前提、适用版本）
- 报错原文（是否逐字，还是凭记忆复述）
- 机制描述（加载顺序、执行时机、边界条件）

**C类·引述与依据**（必须有出处，不能编造）：
- 官方文档的说法（版本、访问日期）
- 他人观点、issue/PR 里的讨论
- 书籍/文章中的论断

**D类·判断性陈述**（检查逻辑而非事实）：
- 因果关系的成立性（"因为改了配置，所以生效了"——真的是这个原因吗）
- 类比的准确性
- 趋势判断的合理性
- **一手性**：这个"我实测/我发现"是真的亲手做过，还是搜来的？

### 步骤2：逐条核查

对提取出的每一条事实，按以下流程核查：

```
提取事实 → 搜索验证 → 交叉比对 → 标记结果
                ↓
         找到权威来源？
           ↙       ↘
         是          否
         ↓            ↓
      数据一致？    标记为 ⚠️ 无法验证
       ↙    ↘        ↓
     是      否    建议删除或模糊化处理
     ↓       ↓
   ✅通过   ❌错误
             ↓
         给出正确数据和来源
```

核查时必须使用搜索工具获取最新、最权威的信息。不能仅依赖AI内置知识——AI的知识本身就可能是事实错误的来源。

**但技术写作有一个财经写作没有的巨大优势：ground truth 就在本地。** 优先级从高到低：

1. **实际跑一遍**（命令、代码、配置）——最强验证，跑得通就是对，跑不通就是错，没有争议空间
2. **读源码 / 打包产物**——文档没写清或有歧义时，源码是唯一真相
3. **翻原始日志 / 终端历史**——报错原文、时间线、当时的实际操作，回去复制而不是复述
4. **实查 API / 后台**——star、下载量、阅读量这类数字当场查，记录查询时间
5. **搜索验证**（外部资料）——以上都拿不到时的兜底，且必须交叉比对

A/B 类事实**优先走 1-4**（本地可验证），C 类走 5（外部搜索）。
凡是本地能验证的断言，却只用搜索结果背书的，审校报告里要标出来："这条可以自己跑一遍确认，不要用搜索结果代替实测。"

**关键心态：AI审校自己写的文章，本质上是"自己检查自己的作业"。这要求格外严格的自我怀疑——你生成这个数据的时候就可能错了，你核查它的时候用的还是同一个大脑，所以必须借助外部验证（跑一遍、读源码、翻日志、搜索）来打破自我验证的循环。**

核查的置信度分级（**本地验证高于外部来源**）：
- **一级置信（✅ 已验证）**：本地实测/读源码确认，或在权威来源中找到完全一致的数据 → 可以安心使用
- **二级置信（🔶 基本可信）**：多个来源大致一致但细节有出入 → 可以使用，但标注"约"或给出区间
- **三级置信（⚠️ 存疑）**：只找到单一来源或来源不权威 → 建议模糊化处理或删除
- **零置信（❌ 无法验证）**：既不能本地验证，搜索后也找不到任何来源支撑 → 必须删除，不能赌

**特别标注**：凡是标为"我实测""我跑了""我读了源码"的断言，只有达到**一级置信**才能这么写。
达不到一级，就必须改口径为"据文档说明""社区反馈""我理解是"——**宁可弱化表述，不可伪造一手性**。

### 步骤3：生成审校报告

审校完成后，按标准格式输出报告（见下方输出格式）。

### 步骤4：给出整改建议

对每个发现的问题，给出具体的修改建议：
- 错误数据：提供正确数据和来源
- 无法验证的数据：建议删除、模糊化（"约""超过""接近"）、或标注出处让读者自行判断
- 逻辑问题：指出因果链的薄弱环节
- 引言问题：提供正确出处或建议改为转述

## 核查标准（按严重程度分级）

### 🔴 红色·致命错误（必须修改，否则不能发布）

- 关键数据完全错误（版本号、耗时、次数、日期等核心数字搞错）
- **命令/代码跑不通**，或参数名、API 签名、配置项名称错误
- **报错原文是编的或凭记忆复述的**（技术读者一眼看穿）
- **一手性造假**：把搜来的结果写成"我实测""我跑了三次""我读了源码"
- 引述编造（把文档没说的话写成"官方文档说"）
- 张冠李戴（把 A 工具的行为说成 B 工具的，把 A 版本的问题说成 B 版本的）
- 泄露敏感信息（token、密码、内网 IP、企业未公开数据、客户名称）
- 公众号渠道出现个股名称 + 买卖暗示/目标价/点位（**必返 errcode 45166 拒稿**）

### 🟡 黄色·重要偏差（强烈建议修改）

- 数据有偏差但量级正确（"约 11.7k tokens"实际是"13.2k"）
- 时间有偏差（"9 月 17 日"实际是"9 月 16 日深夜到 17 日"）
- **实测缺环境说明**（没写系统/版本/硬件/样本量，读者复现不出来）
- **样本量不足却写成规律**（跑一次就写"通常耗时 X 秒"）
- 引述大意正确但措辞不准（转述了但加了引号当直引）
- 遗漏了重要的限定条件（说"不支持"实际是"这个版本不支持"）
- 数据口径不一致（混用下载量/安装量/star 数，混用 ms 和 s）

### 🟢 绿色·轻微瑕疵（建议修改但不影响发布）

- 非核心细节的小误差
- 数据虽准确但缺少出处或查询日期标注
- 翻译/转述存在细微偏差
- 可能引起歧义但不算错误的表述
- 平台差异未说明但不影响主结论（如 macOS 专属命令未标注）

## 技术写作的高频事实陷阱

审校时重点关注以下AI最容易出错的领域，详见参考文件 [common-traps.md](references/common-traps.md)：

- 版本号偏移（v0.12.1 写成 v0.12.0，或用了旧版本的行为描述新版本）
- 命令与参数名拼错（`--min-likes` 写成 `--min-like`，AI 极擅长编造"看起来对"的 flag）
- 单位混淆（ms vs s、MB vs MiB、token vs 字符、次/月 vs 次/日）
- 百分比 vs 百分点、涨跌幅的计算基准
- 报错原文被复述而非复制（细节一定对不上）
- 文档与实际行为不一致却只采信文档
- 同名/近似工具的混淆（不同项目、不同分支、不同语言的同名库）
- 因果关系与相关关系的混淆
- 平台差异被当成通用结论（macOS 能跑 ≠ Linux 能跑）

## 特别核查清单：AI生成内容的系统性风险

AI写作最常产生以下类型的事实问题，每篇AI辅助生成的文章都必须逐项检查：

### 1. 数字幻觉
AI会生成"看起来合理"的数字。这是最常见也最隐蔽的幻觉类型——AI不会给你一个明显离谱的数字（比如"这个命令耗时 900 秒"），它会给你一个"差一点"的数字（比如"11.5k tokens"而实际是"11.7k"）。越合理的数字越要怀疑。
核查方法：文章中每一个具体数字都必须能本地实查或在权威来源中找到对应。找不到的，要么删掉，要么加"约""接近""超过"等模糊限定。**star 数、下载量、阅读量这类必须当场查 API，不许用记忆值。**

### 2. 引述拼接
AI可能把 A 文档的说法安在 B 文档上，或者把某项目的多条 issue 讨论拼接成一句"官方回复"，或者"脑补"一句风格很像官方文档但它根本没说过的话。AI在这件事上可以做到非常一本正经。
核查方法：每条直接引用都要查原始出处（哪个文件、哪个版本、哪次讨论、访问日期）。找不到原始出处的，改为转述大意，不加引号。

### 3. 时间线错位
AI容易搞混相近的日期和版本。比如把 9 月 17 日的事放到 9 月 16 日，把 v0.11 的行为说成 v0.12 的。差一天、差一个小版本，在叙述中不显眼，但被懂行的读者看到就会瞬间失去信任。
核查方法：涉及具体日期和版本号的事件，查证确切时间点。尤其是"XX 版本开始 XX"这种句式，版本和行为的对应关系必须逐一确认。

### 4. 因果虚构
AI倾向于把时间上先后发生的事件描述为因果关系。"我改了配置，然后它生效了"在AI笔下很容易变成"因为改了配置，所以生效了"——而真实原因可能是你顺手重启了服务。
核查方法：看到"导致""因此""于是"等因果词时，问自己：如果A没发生，B就一定不会发生吗？有没有其他同期变更可能是真正的原因？不确定的话，用"在此之后""在XX背景下"替代因果表述。

### 5. 幸存者偏差
AI在举案例时倾向于挑选支持结论的证据，忽略反面案例。比如讲"这个方案很稳定"时只举成功的三次，不提失败的那次；讲"自动化省时间"时不提维护它花掉的时间。
核查方法：每一个用案例支撑的结论，都要问——有没有反例？**技术文里"代价"和"失败"往往是文章最有价值的部分**，如果有显著反例，必须在文章中至少提一句。

### 6. 权威性伪装
AI最危险的幻觉不是"明显瞎编"，而是"以一种极其自信和专业的语气说出不准确的话"。它不会说"我猜大概是"，它会直接告诉你"根据源码"——然后那段源码不存在。越专业的表述越要警惕。
核查方法：文章中所有以"源码显示""文档说明""实测表明""数据显示"开头的句子，必须逐一验证其依据是否真实存在。**"源码显示"后面必须能给出文件路径，"实测表明"后面必须能给出环境。**

### 7. 一手性伪装（本号专属，最严重）
AI 会把搜来的、推理出的内容写成"我实测""我跑了三次""我发现"。这是**人设层面的造假**，比数据错一位严重得多——你的定位就是"真做出来了"，一旦被读者发现某处是包装的，整篇文章乃至整个账号的可信度都会崩。
核查方法：文中每一处第一人称的实操表述，逐条问用户："这个你真做过吗？在哪做的？"
- 真做过 → 要求补上环境（系统/版本/时间），达到一级置信
- 没做过 → **必须改口径**为"据文档""社区反馈""我理解是"，或干脆删掉
- 不确定 → 标红，交用户裁决，**不许默认放过**

## 审校者的自我怀疑协议

这是从笛卡尔怀疑论推导出的一组自我约束规则。审校不只是对文章的怀疑，更是对自己的怀疑：

**1. 怀疑自己的记忆。**
"我记得这个命令是这么写的"——不够。记忆不是证据。**跑一遍**才是。

**2. 怀疑自己的判断。**
"这个数字看起来合理"——不够。合理不等于正确。"11.5k"和"11.7k"都合理，但只有一个是对的。

**3. 怀疑搜索结果的质量。**
不是所有搜索结果都可信。论坛帖子、自媒体文章、百科类条目、**过期的技术博客**都可能有错。优先信任：源码 > 官方文档 > 维护者在 issue 里的回复 > 权威技术媒体 > 社区讨论 > 二手教程。特别注意时效——一年前的教程可能整篇已失效。

**4. 怀疑"众所周知"的信息。**
越是"大家都这么说"的信息，越可能从未被认真验证过。"这个配置改完重启就生效"——所有人都这么说，但没人告诉你重启的到底是服务还是会话。技术圈流传的"常识"里，藏着大量从未被验证的版本残留。

**5. 怀疑自己的实测。**
"我跑过一次是这个结果"——一次不等于规律。样本量、环境、偶然因素都要交代。**跑一次的结果只能写"我这次是"，不能写"通常"。**

**6. 标注自己的不确定性。**
审校报告中如果某条信息自己也无法100%确认，必须如实标注"审校者也无法完全确认，建议用户自行核实"，而不是因为"大概率对"就标为通过。诚实地说"我不确定"，远好过自信地给出一个可能错误的背书。

**7. 区分"没验证"和"验证为假"。**
这两者在报告里必须分开标。"我没找到依据"是可接受的（改口径或删除即可）；"我验证了，它是错的"必须给出正确值。混为一谈会让用户不知道该改还是该删。

## 评分标准

| 分数 | 含义 | 发布建议 |
|------|------|---------|
| 9-10 | 事实高度可靠，无错误或仅有极轻微瑕疵 | 放心发布 |
| 7-8 | 基本可靠，有少量偏差但无致命错误 | 修改偏差后发布 |
| 5-6 | 存在明显问题，需要修改多处 | 修改后重新审校 |
| 3-4 | 多处严重错误，可靠性存疑 | 建议重写相关段落 |
| 1-2 | 事实基础不可靠 | 建议暂缓，重新搜集素材 |

## 参考文件

当需要了解技术写作中最常见的事实陷阱和易错点时，读 [common-traps.md](references/common-traps.md)。

**与 material-collector 的分工**：`material-collector/references/fact-check.md` 管**素材入库前**的核查（搜集阶段），本 skill 管**成稿后**的审校（发布前）。前者是逐条素材的验证，后者是全文的系统性扫描 + 一手性核查。两者不重复：素材阶段查过的，成稿阶段仍要查"是否被 AI 在写作中改写走样"。

## 额外提示

- 审校必须做实际验证，不能仅凭AI内置知识判断对错——AI的知识本身就是最大的风险源。这一条是铁律中的铁律，没有例外。
- **技术文的验证优先级：跑一遍 > 读源码 > 翻日志 > 实查API > 搜索。** 前四种是本地可验证的，比任何外部来源都硬。凡是本地能验证却只用搜索背书的，要在报告里指出来。
- AI告诉你的任何东西，都记得先验证一下。这不是多疑，是负责。
- 审校过程中如果发现某条数据在多个来源中说法不一，应如实报告分歧，不替用户做判断。
- 对于观点性判断（如"大概率""我认为"），审校系统不做对错评价，只检查其论据是否有事实基础。
- 审校报告的"已验证事实"部分同样重要——它让用户知道哪些内容已经确认无误，增强发布信心。
- **一手性存疑项必须交用户裁决，不许默认放过。** 这是本号的信任底线：数据错了是无心之失，一手性造假是人设崩塌。审校时宁可多标几处让用户确认，也不要放过一处包装。
- 如果时间允许，建议每篇文章至少做两轮审校：第一轮由AI完成系统性核查，第二轮由用户自己对标红项和一手性存疑项做人工确认。
- **事实洁癖的终极检验**：发布前问自己一个问题——"如果这篇文章里的每一个数字、每一段代码、每一条报错、每一个'我实测'都被一个很较真的读者逐条复现，我会不会心慌？" 如果会，那就还没到能发的程度。
