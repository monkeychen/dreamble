# 技术写作高频事实陷阱

> 本文件列出了技术类公众号文章中最常出现的事实错误类型。
> 审校时按本清单逐类扫描，可以捕获 80% 以上的常见错误。
>
> **本号的特殊性**：读者会去复现。命令跑不通、参数对不上、版本号不符，
> 复现失败的那一刻，你后面说的所有话他都不信了。所以技术文的事实错误代价比一般内容更高。

---

## 一、数字类陷阱

### 1. 单位与量级混淆

这是技术写作中最隐蔽的错误之一，因为数字看起来都"很合理"。

| 错误 | 原因 | 正确做法 |
|------|------|---------|
| "耗时 3 秒" 实际是 3 毫秒（或反之） | ms / s 混淆 | 标明单位，超过 1000ms 换算成 s |
| "文件 100MB" 实际是 100MiB | MB（10^6）vs MiB（2^20），差 4.86% | 统一口径，或标明是哪种 |
| "11.7k tokens" 其实是字符数 | token ≠ 字符（中文约 0.7 token/字） | 标明是 token 还是字符，说明估算方法 |
| "每月 237 次下载" 其实是每日 | 时间口径混淆 | 标明统计窗口（last-month / last-day） |
| "内存占用 8G" | GB vs GiB，且没说是否含 swap | 标明测量方式（RSS / VSZ / 峰值还是常驻） |
| "下载量 568" | 混淆 release 下载 / npm 安装 / star | 三者口径完全不同，必须分开说 |

### 2. 百分比 vs 百分点

这个错误出现频率极高，技术媒体也常犯。

- ❌ "成功率从 90% 提升到 95%，提升了 5%" → 实际提升了 5 个**百分点**，相对提升是 5.6%
- ❌ "耗时降低了 30%" → 是从多少降到多少？基数不同结论差很多
- ✅ 表述要求：涉及比率的变动，必须区分"百分点"和"百分比"，或干脆给绝对值

### 3. 性能数据的基准

- ❌ "快了 3 倍" → 从多少到多少？3 倍是 (新-旧)/旧 还是 旧/新？
- ❌ "启动时间 200ms → 3s" 不说是什么环境 → 冷启动还是热启动？首次还是后续？
- ❌ "跑一次 5 秒" → 跑一次不等于通常。样本量呢？
- ✅ 性能数据必须给：基线值、新值、环境、样本量、取值方法（平均/中位/最好一次）

### 4. 估算值伪装成实测值

- ❌ "约 11.7k tokens" 其实是按 0.7 token/字估的，却写成"实测" → 这是估算，不是实测
- ❌ "下载量 800+" 其实是把几个渠道加起来估的
- ✅ **估算就写估算**，并说明估算方法。估算值不能标为"实测"——这是本号一手性底线的一部分

### 5. 同比 vs 环比 / 累计 vs 区间

- 同比：跟去年同期比；环比：跟上一个周期比。两者差异可能很大，不标注口径会误导
- 累计下载量 vs 区间下载量：568（累计全部 release）≠ 13（最新版本）
- npm 下载量的 "last-month" 是滚动 30 天，不是自然月

## 二、版本与时间线类陷阱

### 1. 版本号偏移

AI 最常犯的错误，也是最容易被读者抓到的。

| 常见错误 | 后果 |
|---------|------|
| v0.12.1 写成 v0.12.0 | 读者装错版本，复现不出你的结果 |
| "从 v2.0 开始支持" 实际是 v2.3 | 误导读者的升级决策 |
| 用旧版本的行为描述新版本 | 整篇文章的前提就是错的 |
| 把 patch 版本的修复说成 minor 版本 | 影响读者判断要不要升级 |
| 版本号写成日期或反过来 | `2026.09` vs `v2.6.9` 这类容易混 |

**审校原则**：文中每一个版本号都要能对应到实际的 release / changelog 条目。
查不到对应条目的版本号，标红。

### 2. 时间线错位

- 事件的日期：9 月 17 日 vs 9 月 16 日深夜（跨零点的排查尤其容易记错）
- "改了配置之后生效" —— 真的是配置的作用吗？还是你顺手重启了服务？
- 依赖更新的顺序：先升级 A 还是先改 B，影响因果叙述
- commit 时间 ≠ 部署时间 ≠ 问题发生时间

### 3. 行为的多个版本

同一个行为在不同来源中说法可能不同，取决于：
- 说的哪个版本
- 哪个平台（macOS / Linux / Windows）
- 哪种安装方式（npm 全局 / 本地 / 包管理器 / 源码编译）

审校原则：选择与自己实际环境一致的来源，并**标明版本和平台**。

### 4. 因果关系的简化

- ❌ "改了 `.gitignore` 就好了" → 可能真正起作用的是同时执行的 `git rm --cached`
- ❌ "升级依赖解决了这个问题" → 可能只是重启清掉了缓存
- ❌ "平台封了我的 IP，因为那个 CVE" → 归因需要证据，不能凭时间接近就认定
- ✅ 使用"催化""加剧""在 XX 之后""可能相关"等措辞，避免过于简单的因果归因
- ✅ **因果断言的标准**：能说清"如果 A 没发生，B 就一定不会发生吗"，才能写"因为"

## 三、引述与依据类陷阱

### 1. 高频被错误归属的技术说法

| 常见误引 | 真实情况 |
|---------|---------|
| "官方文档说支持 XX" | 文档没写，是某篇博客说的；或文档写的是另一个版本 |
| "这是 XX 的设计哲学" | 是某位维护者在 issue 里的个人回复，不代表官方立场 |
| "业界标准做法是……" | 往往找不到依据，是 AI 的口头禅 |
| "大家都知道 XX 很慢" | 没有基准数据支撑的印象 |
| "XX 之父说过……" | 技术圈的名言归属错误率和金融圈一样高 |
| "这个 API 已经废弃了" | 可能是标记 deprecated 但仍可用，也可能你看的版本旧了 |

### 2. 文档与实现不一致（技术写作特有的富矿）

这是技术文最有价值的素材，也是最容易出错的地方：

- **文档滞后于实现**：文档说支持，实测不支持（或反之）
- **文档省略前提**：文档说"支持覆盖"，没说覆盖顺序由文件名字典序决定
- **文档没写边界**：只写了正常路径，没写什么情况下失效
- **不同页面互相矛盾**：快速开始和 API 参考说的不一样

审校原则：**两边都记下来**，标明"文档说 X，实测是 Y"。
只采信文档而不实测的断言，标黄——"这条可以自己跑一遍确认"。

### 3. 引述验证的优先级

- 源码 > 官方文档 > 维护者在 issue/PR 里的回复 > 官方 changelog > 权威技术媒体 > 社区讨论 > 二手博客
- 能找到原文出处（哪个文件、哪一行、哪个版本、访问日期）→ 直接标注
- 找不到原文但被广泛转引 → 使用"据传""社区普遍反馈"等限定语
- 完全无法验证 → 改为转述大意，不用引号，或删除

## 四、工具与命名类陷阱

### 1. 同名混淆

技术圈的同名问题比金融圈更严重：

- 同名不同项目：多个叫 `xxx-cli` 的包，作者不同、功能不同
- 同名不同语言：Python 的 `requests` vs JS 的 `request`（已废弃）
- 同项目不同分支：fork 出去的版本行为已经分叉
- 改名遗留：旧名和新名并存，教程混用（如 `create-react-app` 的各种替代品）
- 大小写与连字符：`GitHub` vs `Github`、`node-js` vs `nodejs`、`WebPack` vs `webpack`

### 2. 命令与参数混淆

**AI 编造参数名的能力极强**，这是技术文最危险的幻觉类型：

- ❌ `--min-like` 实际是 `--min-likes`（少个 s）
- ❌ `-rf` 写成 `--rf`（短参 vs 长参）
- ❌ 参数顺序错了：`command --flag value` vs `command value --flag`
- ❌ 子命令层级错：`npm run publish` vs `npm publish`（完全不同的两个东西）
- ❌ 平台差异：macOS 没有 `timeout` 命令；BSD grep 不认 `\|` 交替；`sed -i` 在 macOS 需要参数

审校原则：**每一条命令都必须实际跑过**。跑不通就是红色错误，没有商量余地。

### 3. 路径与环境混淆

- ❌ 硬编码私人路径 `/Users/chenzhian/...` 出现在文章里（泄露 + 读者跑不通）
- ❌ 项目级路径和用户级路径混用（`./.workbuddy/skills` vs `~/.workbuddy/skills`）
- ❌ 沙箱路径和真实路径混为一谈
- ❌ 未说明需要的环境变量或前置安装

### 4. 数据时效

- star / fork / 下载量变化频繁，引用时必须标注查询日期
- "当前版本 XX" —— 这个"当前"是什么时候？
- 依赖的最新版本号，一周就可能变

## 五、逻辑类陷阱

### 1. 相关性 ≠ 因果性

- ❌ "每次我加了这个配置，构建就变快了" → 样本几次？有没有控制其他变量？
- ❌ "star 涨了，说明文章写得好" → 可能是同期某个大 V 转发了
- ✅ "在我这 3 次测试中，加了配置后构建时间从 X 降到 Y，但环境有其他变化，不能确定归因"

### 2. 幸存者偏差

- ❌ "这个方案很稳定，我用了三个月没出问题" → 出过问题但没提
- ❌ "自动化省了很多时间" → 没算维护它花的时间
- ❌ 举成功案例时不提失败的尝试
- ✅ 提及成功案例时，至少简要承认代价和失败情况。**技术文里"代价"往往是最有价值的部分**

### 3. 样本量不足

- ❌ "跑一次是 5 秒，所以通常 5 秒" → n=1 得不出"通常"
- ❌ "试了三次都成功，说明这个方法是可靠的"
- ✅ **样本 <5 的统计结论，必须标注"样本太少，不能判断"**（这条同样适用于运营数据复盘）

### 4. 基数效应

- ❌ "下载量增长了 100%" → 从 1 到 2 也是 100%
- ❌ "star 增速放缓了" → 基数大了之后增速自然放缓，要看绝对值
- ✅ 讨论增长率时必须给基数。小基数下的高增长率没有意义

### 5. 以偏概全

- ❌ "这个工具不支持 XX" → 可能只是你用的版本不支持，或你的环境不支持
- ❌ "AI 都会编造参数名" → 应表述为"AI 容易编造参数名，所以必须验证"
- ✅ 使用汇总性判断时标注适用范围：版本、平台、场景

### 6. 把"没验证"当成"验证为假"

- ❌ "文档里没找到这个配置项，所以不存在" → 文档没写 ≠ 不存在，源码里可能有
- ❌ "搜不到这个报错，所以是我环境的问题" → 搜不到也可能只是没人写过
- ✅ 严格区分"我查了没有"和"它不存在"。前者可以说，后者需要读源码或做穷举验证

## 六、审校快速扫描法

拿到一篇文章后，按以下顺序快速扫描：

**第一遍：扫数字**
标记所有具体数字（版本号、耗时、次数、大小、日期、star/下载量）。这些是最需要核查的，且**大部分可以本地实查**。

**第二遍：扫命令和代码**
标记所有代码块、命令、配置片段、参数名。**逐条实际跑一遍**（或在源码里核对）。
顺带扫敏感信息：token、密码、内网 IP、私人路径、企业数据。

**第三遍：扫一手性**（本号专属，最重要）
标记所有第一人称实操表述："我实测""我跑了三次""我读了源码""我发现""排查了两天"。
**逐条问：这个真做过吗？环境交代了吗？** 达不到一级置信的，改口径或删除。

**第四遍：扫引述**
标记所有"文档说""官方说""源码显示""社区反馈"。逐条要出处：哪个文件、哪个版本、访问日期。
找不到出处的，改为转述大意或删除。

**第五遍：扫因果**
标记所有因果表述（"因为""导致""所以""于是""结果"）。每一个因果链都要问：
这个因果关系成立吗？有没有同期变更被忽略了？不确定就改成"在此之后"。

**第六遍：扫程度**
标记所有绝对化表述（"所有""从来没有""每次都""一定""永远""不支持""必然"）。
这些通常需要软化成"在我的测试中""这个版本""大概率"。

## 七、发布前红线（任一触发即不可发布）

- [ ] 有命令/代码**没实际跑过**就写进了文章
- [ ] 有报错是**凭记忆复述**的，不是从日志复制的
- [ ] 有"我实测"的表述**达不到一级置信**（没做过、没环境、样本为 1 却写成规律）
- [ ] 代码块里残留 **token / 密码 / 内网 IP / 私人路径 / 企业数据**
- [ ] 有版本号或 API 签名**查不到对应依据**
- [ ] 公众号渠道出现**个股名称 + 评级/目标价/点位**（必返 errcode 45166）
- [ ] 有"业界普遍认为""大家都知道"这类**无依据的权威伪装**
