# 复盘协议

> 本文件定义**怎么做复盘**：表结构、判读规则、目标推导原则、月度复盘流程。
> **本文件不含任何具体数据。** 数据在 `content-ops/`（业务流水），见下方「数据在哪」。

---

## 数据在哪（skill 不存状态）

方法论稳定，业务数据高频变化，两者分开存放：

| 需要什么 | 去哪读 |
|---|---|
| 历史选题与筛选理由 | `content-ops/topic-log.md` |
| 单篇文章的完整复盘 | `content-ops/reviews/<日期>-<slug>.md` |
| 当前数据基线（产能、star、下载量） | `content-ops/baseline.md` |
| 当期目标值与推导依据 | `content-ops/goals/<周期>.md` |

`content-ops/README.md` 定义了目录约定和数据纪律。**skill 文件里不写具体数字**——
写了就会过期，而过期的数字比没有数字更危险（AI 会当成现状引用）。

## 一、单篇复盘表（发布后 7 天内填）

复制到 `content-ops/reviews/<日期>-<slug>.md`，文件名与 `site/content/posts/` 的目录名一致。

```

所用角度模板：亲手验证 / 决策解剖 / 根因追踪 / 成本核算 / 反直觉数据 / 机制翻译 / 历史平行 / 跨界迁移

—— 站点数据（GoAccess / 百度统计）——
```

**填写纪律**：

- 判断部分写"实际发生了什么"，不写"我本来以为"

## 二、判读规则

**跟自己历史中位数比，不跟别人比。** 不要照搬其他账号的"优秀线"。

| 现象 | 说明 | 下一步 |
|---|---|---|
| 阅读高、关注低 | 内容有吸引力，但关注理由不清楚 | 检查文末引导与账号定位表达 |
| 打开低、分享高 | 内容本身不错，标题/封面/摘要拖后腿 | 优化标题结构 |
| 阅读高、分享低 | 选题有热度，但缺可转发的观点或工具 | 补"读者能拿走什么" |
| 评论集中问同一问题 | 下一篇选题已经出现 | 直接进 `topic-log.md` |
| 某内容线连续表现稳定 | 可以系列化 | 提高该线比例 |
| star 涨但 issue 为 0 | 被看见了，没被用起来 | 检查上手门槛和文档 |
| **样本 < 5 篇** | **不能判断** | 继续积累，**不要改策略** |

### 样本量红线

任何"某类内容表现更好"的结论，**样本必须 ≥ 5 篇**。低于此值一律标注"样本太少，不能判断"，
并继续按现有策略积累。

这条纪律的作用：防止第 3 周就凭两篇文章的波动推翻整套定位。
低频产能下（如每周一篇），攒够 5 篇同类型样本需要一个多月——**在那之前不要动策略**。

## 三、目标推导原则

制定任何周期目标时遵守：

### 1. 从历史数据推导，不从意愿推导

先查 `content-ops/baseline.md` 的历史产能，再定目标。

> **反面案例（真实发生过）**：定位咨询中曾按理想值建议"每周 2 篇"，
> 而公众号历史产能是 0.8 篇/周——目标是历史的 **2.5 倍**。
> 定高于历史产能的目标，必然导致第 3 周断供。

**推导方法**：历史频率 × 周期长度，向上取整后**只加少量余量**（不超过 25%）。
如果确实要提速，先说明"多出来的产能从哪个既有项目挪来"。

### 2. 主指标必须完全可控

不挂商业动作时，验证信号只能来自自己能做到的事：

| 可控性 | 指标类型 | 用途 |
|---|---|---|
| **完全可控** | 发布篇数、复盘完成率、选题库累积数、档案修订次数 | **做主指标** |
| 半可控 | star、下载量、issue 数 | 做辅指标 |
| 不可控 | 涨粉、阅读量、收入 | **只记录，不设目标** |

用不可控项做主指标的后果：目标达不达成取决于平台推荐和转发运气，90 天结束你什么都验证不出来。

### 3. 辅指标看"被真用起来"，不看虚荣数字

优先级：**issue 数 > 下载量 > star 数**

star 是虚荣指标（点了不一定用），下载量说明装了，issue 说明真在用并遇到了真实场景。
对"做一个有意义的开源项目"这个动机，**有人报 bug 就是成功**。

### 4. 不设无法验证的目标

不写"90 天涨到 X 关注"、"实现 Y 收入"这类预测。
每个目标必须能回答："周期结束时，我用什么数据判断它达没达成？"答不上来就不设。

## 四、月度复盘流程

```
请读取 content-ops/baseline.md、content-ops/goals/<当期>.md、
content-ops/topic-log.md 以及 content-ops/reviews/ 下过去 4 周的复盘文件，
为我完成月度复盘。

先复盘：
1. 刷新 baseline.md 的所有数据（GitHub API / npm API / 公众号后台实查，
   记录查询日期；查不到的标"待补"，不要用文件里的旧数字）
2. 哪些内容线高于我自己的历史中位数（样本 <5 篇的明确标注"不能判断"）
3. 哪些标题带来点击但没带来分享或关注
4. 哪些角度模板表现最好（亲手验证 / 决策解剖 / 根因追踪 / ...）
5. 读者反复提出了哪些问题
6. 当期 goals 的主指标逐项给"达标 / 滞后 / 无法判断"，滞后的写清原因
7. 辅指标的开源项目数据变化
8. 哪些结论样本太少，暂时不能判断

再更新：
9. 把刷新后的基线值和目标进度写回 baseline.md 和 goals/<当期>.md 的进度记录表
10. 下个月的选题规划（按当期 goals 文件里的产能目标，标注内容线和角度模板），写入 topic-log.md
11. 方法论需要修订的地方（改哪条、为什么）——改 skills/ 下对应文件，不改本文件的数据

不要为了填满排期生成重复内容。如果产能不够，直接建议减少篇数。
```

## 五、周期切换

一个周期（季度）结束时：

1. 在 `goals/<当期>.md` 末尾补封存清单（见该文件的模板），状态改为"已封存"，**不删除**
2. 新建 `goals/<下期>.md`，目标值**重新从刷新后的 baseline 推导**，不沿用上期数字
3. 如果方法论要变（比如内容线比例调整、评估维度增减），改 `skills/topic-selector/SKILL.md`
   并在其变更记录里写明原因
4. `topic-log.md` 继续追加，不清空

> **分清两种改动**：改目标是记账（写 goals），改方法论是改做法（写 skills）。
> 两者混在一个文件里，是这份协议要防止的事。
