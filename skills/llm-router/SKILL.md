# 大模型选型路由

把选型问题收敛为一张可执行的决策卡：选哪个**服务商与模型**、推理开到什么程度、采用它的边界，以及效果或成本不合预期时如何调整。

## 先分清三件事

1. **服务与模型分开选。** 联网、网页抓取、文件检索、代码执行、区域部署、账单与数据留存是服务/平台能力；推理质量、上下文、多模态和延迟才是模型能力。不得因某模型在某个网关可用，就推断其原厂 API 也有同样工具。
2. **先定统一推理等级，再映射厂商参数。** `low`、`high`、thinking budget 等参数在不同厂商之间没有可比性。用 L0–L4 表达任务需要的推理深度，再查厂商映射。
3. **动态事实与方法分开。** 型号存活、价格、参数名、地区能力、折扣和工具可用性都是动态事实；在给出具体型号、金额或可复制调用代码前，必须用该服务商的官方文档或控制台核验。无法核验时，给条件性建议，不得编造模型 ID、参数或价格。

## 决策顺序

### 1. 提取约束并标明假设

从任务中识别：任务目标、候选服务商/模型、实时信息或工具需求、上下文量、输入模态、交互时延、错误代价、数据区域/私有化要求、预算与预计调用量。

用户未说明的内容不要为了凑条件反复追问。采用合理默认并在结论中标为“假设”；只有某个未知约束会让推荐在两个方向之间翻转时，才提出一个简短问题。

数据合规不能用“国产/海外”替代判断。须区分部署地域、调用链是否经过网关、日志与数据留存、合同要求及是否必须私有化；不明时明确标为待确认。

### 2. 先过滤，再比较

按以下优先级过滤候选项：

1. 数据、地域、私有化、可用账号与预算上限等硬约束；
2. 是否具备任务所需的输入模态、上下文、工具和结构化输出；
3. 时延与吞吐要求；
4. 质量、推理粒度、单次任务的预期成本与接入复杂度。

需要实时资料时，先判断谁提供当前可用、可审计的检索或抓取链路。检索能力不等于推理能力，也不能由提高 effort 替代。已有自建检索管线时，比较模型本身；没有时，要把工具调用、网页内容 token 和失败重试一并计入成本。

### 3. 定 L0–L4 与型号档位

读取 [任务分类](references/task-taxonomy.md) 定推理等级。上下文规模决定模型档位，不自动提高 reasoning：长材料综合首先选择能稳定容纳材料的模型，必要时先分层压缩。

- L0：固定映射，如分类、抽取、格式转换；
- L1：单文档摘要、翻译、常规短写作；
- L2：跨文档综合、多文件开发、常规工具循环；
- L3：复杂调试、架构权衡、深度审查；
- L4：研究级难题、长程自主执行或高风险最终复核。

默认从满足约束的较低 effort 开始。只有在可复现评测、人工抽检或业务错误成本证明收益时才升档。批量任务优先考虑 cascade：低档先跑、用 schema/单测/规则判失败，再把失败样本升级；没有可靠失败判定时，不要承诺 cascade 会省钱。

### 4. 映射为服务商参数

读取 [厂商参数映射](references/effort-mapping.md)，并在输出中如实说明粒度损失：

- 目标等级无法关闭或无法达到时，换模型/服务商，或明确接受降级；
- 某厂商的多个等级映射为同一参数时，说明不能精确表达，而不是假装有差别；
- 调用代码必须以已核验的 SDK、API 版本和端点为准。网关兼容层参数不自动等同于原厂参数；
- 只有在用户需要接入时才给代码；只问“选哪个”时不塞调用样板。

### 5. 核验动态结论

需要具体推荐时，读取 [厂商画像](references/vendor-profiles.md) 作为候选假设，再逐项核验涉及的服务商官方文档：模型 ID 与状态、参数语法与默认值、区域/工具能力、计费与长上下文阶梯。引用或链接支撑“当前”结论的官方页面，并标出核验日期。

参考资料中的历史价格、促销和基准成绩只能帮助筛选，不能作为当前报价。官方资料相互冲突或无法确认时，保守排除该动态能力，并告诉用户缺少哪项证据。

## 输出：决策卡

默认只给一个主推和一个有明确取舍的备选，不做没有排序依据的“全家桶”。

```markdown
## 结论
主推：<服务商/平台> · <模型> · <L 等级与已核验参数>
备选：<仅在何种条件下更优；没有有意义备选则省略>

## 判断依据
- 任务与假设：<目标、上下文、时延、错误代价、未确认约束>
- 硬约束：<通过/排除的原因>
- 为什么选它：<2–3 条与任务直接相关的原因>

## 接入配置
<仅在需要接入时给出、且已核验的最小代码或 JSON；注明平台与 API 版本>

## 成本、风险与验证
- 成本模型：<输入、输出、工具调用、缓存、重试和长上下文阈值中实际相关的项>
- 已核验：<官方来源与日期>
- 上线前验证：<代表性任务集、质量阈值、延迟/成本上限>

## 调整路径
- 质量不足：<升 effort、升档或更换模型的明确条件>
- 成本/延迟超标：<降 effort、裁剪上下文、batch 或 cascade 的明确条件>
```

不要把隐藏推理过程当成证据。给出任务层面的理由、可观察的权衡和可复现实验标准即可。

## 落地绑定

选型结论要能在 WorkBuddy 里执行才有意义。三条路，按优先级选：

| 路径 | 能选什么 | 能控什么 | 代价 |
|---|---|---|---|
| `.codebuddy/agents/<name>.md` 的 `model` 字段 | 仅 `~/.codebuddy/models.json` 池内模型 | 仅 `effort` | 零配置，密钥由平台代持 |
| skill 自带脚本直连 API | 任意厂家、任意端点 | 全部参数，含厂家私有参数 | 自管密钥、自己写代码 |
| 环境变量 `CODEBUDDY_CODE_SUBAGENT_MODEL` | 池内模型，全局覆盖 | 只换模型，不控 effort | 一次性，用于临时对拍 |

**多阶段任务走第一条**：一个阶段一个 agent 文件，`model` + `effort` 写进 frontmatter，
skill 只负责编排派发顺序。改模型只改 frontmatter，编排逻辑不动。

四个已验证的坑：

- 模型 id 必须精确匹配 `models.json` 里的 `id` 字段，否则**静默降级**为继承主会话模型——
  只在日志里 warn 一句，界面上看不出来
- `models.json` 中 `supportsReasoning: false` 的模型上，`effort` 字段不生效
- 新增或修改 agent 文件后**新开会话最稳**：`/agents` 管理器监听配置变更会热重载，
  但 ProductProvider 那条加载路径不保证，当前会话派发大概率报 "agent lookup failed"
- `models.json` 含明文 apiKey，不要提交进 git

## 确定性初筛

需要可复现的离线初筛时可运行 `scripts/route.py`。它只使用仓库内的静态能力表，输出必须标为“待官方核验”，不能直接拿它的型号、参数或成本结论上线。运行后仍按上面的第 5 步核验。

## 独立发布约束

复制整个 `llm-router/` 目录即可使用；不得依赖仓库根目录、父目录或其他 Skill。
