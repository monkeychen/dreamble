# AI 开发流程规范（提示词模板）

> **用法**：把本文件复制到项目根目录（建议命名 `dev-process.md`，或并入项目 `AGENTS.md`）。
> 新会话开场对 AI 说：「读取 dev-process.md，从当前阶段继续」。
> **核心机制**：一个产品版本一份 PRD；PRD 内按里程碑推进，每个里程碑走「设计 →（UI 原型）→ TDD 开发 → 自动化测试」循环；人类在每个门禁点审核放行。

---

## 总则

- **产品版本号格式 `vx.y.z`**（业界语义化版本标准）：`0.x` 快速迭代期（接口可能变）；`1.0` 首个对外稳定版；`1.x+` 语义化——不兼容变更升主版本，新功能升次版本，修复升修订号。
- **流程结构**：版本 → PRD → 里程碑 M1…Mn 依次推进 → 全部里程碑完成 → 交付出版本 → 进入下一版本。
- **每个门禁点停下等人类审核**，通过后才进入下一步：PRD 审核、spec 审核、prototype 审核、里程碑验收、版本交付。
- **编码一律 TDD**：先写测试、后写实现，红-绿-重构循环；每个功能点必须有单元测试用例。
- **测试全部自动化**：单元、集成、e2e 测试都必须能一条命令自动执行，禁止依赖开发者手工操作。
- **需求变更必须走流程**：先改 PRD → 评估受影响里程碑的 spec → 才动代码。禁止闷头改。
- 所有文档结论先行，禁止空话套话；数据须有出处，没有就标「待补数据」。

## 文档与目录规范

### 目录结构

```
docs/
├── prd/
│   └── PRD-v0.1.0.md              # 一个产品版本只对应一份 PRD
├── spec/
│   ├── spec-v0.1.0-m1.md          # 每个里程碑一份设计文档
│   └── spec-v0.1.0-m2.md
├── prototype/
│   └── prototype-v0.1.0-m1.html     # 涉及前端 UI 的里程碑才有（HTML 高保真原型）
├── release/
│   └── release-v0.1.0.md          # 版本交付记录
├── vibe-coding-log.md             # 大模型协作踩坑记录（持续追加，跨版本共用）
└── archive/
    └── v0.1.0/                    # 版本交付后，该版全部文档整组归档于此
```

### 命名规则

| 文档 | 格式 | 示例 | 位置 |
|---|---|---|---|
| 产品需求 | `PRD-vx.y.z.md`（x.y.z 与产品版本严格一致） | `PRD-v0.1.0.md` | `docs/prd/` |
| 里程碑设计 | `spec-vx.y.z-m<编号>.md` | `spec-v0.1.0-m1.md` | `docs/spec/` |
| UI 高保真原型 | `prototype-vx.y.z-m<编号>.html` | `prototype-v0.1.0-m1.html` | `docs/prototype/` |
| 版本交付记录 | `release-vx.y.z.md` | `release-v0.1.0.md` | `docs/release/` |
| 协作踩坑记录 | `vibe-coding-log.md`（唯一，持续追加） | — | `docs/` |

### 文档状态门禁（所有文档第一行 frontmatter）

```markdown
---
doc: PRD | spec | prototype | release
product: v0.1.0
milestone: m1        # PRD/release 此字段为 -
date: 2026-09-28
status: draft | reviewing | approved
---
```

- `status` 按 draft → reviewing → approved 流转，**approved 才能进入下一步**。
- HTML 原型文件的状态标记写在文件头部注释：`<!-- doc: prototype | product: v0.1.0 | milestone: m1 | status: draft -->`，流转规则相同。
- 版本内文档修订：同名更新（版本号不变），修订前旧内容如需留痕移入 `docs/archive/drafts/`。

## 阶段一：需求（每个版本一次）

**目标**：对齐本版做什么、不做什么、拆几个里程碑、每个里程碑做到什么程度。

- **V1（首个版本）**：先向我澄清（一次性问完，每个问题给建议值让我选，不留空白）：目标用户与核心场景 / 范围边界 / 技术栈与运行环境（如未指定给推荐及理由）。
- **V2+**：基于上一版交付记录与遗留 backlog 规划增量。

**产出 `docs/prd/PRD-vx.y.z.md`**，章节结构：

1. 背景与目标：一句话说清解决什么问题、对用户的价值
2. 用户故事：As a… I want… So that…
3. 功能需求：编号 F1、F2…（全局连续，跨版本接续；废弃的保留编号并标注 `[已废弃@vx.y.z]`），每条附验收标准（AC），AC 同样编号
4. 里程碑划分：M1…Mn，每个里程碑包含——目标、覆盖的 F/AC 清单、是否涉及前端 UI（决定是否需要 prototype）、是否涉及外部系统/接口（决定集成与 e2e 测试范围）
5. 非目标：明确本版不做的事，防止范围蔓延

**格式硬性要求**：

- AC 必须可验证——能写成测试、命令或可观察的行为，禁止「体验良好」这类无法核对的描述
- 全文使用编号引用（F/AC/M），禁止「上述功能」「之前提到的」这类模糊指代

⛔ PRD status 变为 approved 前，不得启动任何里程碑。

## 阶段二：里程碑循环（M1…Mn 依次执行，每个里程碑完整走 2.1–2.4）

### 2.1 设计

**产出 `docs/spec/spec-vx.y.z-m<n>.md`**，章节结构：

1. 本里程碑目标与覆盖的 F/AC
2. 关键功能设计思路：每个关键功能的实现方案、数据流、边界处理
3. 数据模型 / 接口定义（如适用）
4. 关键决策记录：每个重要决策写清「为什么这么选、对用户的影响、放弃了什么」
5. 测试策略：单元测试清单（按功能点列出，TDD「红」阶段以此为准，标注单元/集成）；涉及外部系统/接口的列出集成测试用例与 e2e 场景
6. Task 拆分（表格）：编号 / 内容 / 覆盖 AC / 依赖 / 状态——单个 Task 须可在一次会话内完成、可独立验证
7. 界面与 F/AC 映射（涉及前端 UI 时）：列出 prototype HTML 中每个界面对应覆盖的 F/AC，及关键交互说明、视觉规范（配色/字体/间距）

⛔ spec status 为 approved 后才能进入下一步。

### 2.2 UI/UX 高保真原型（仅涉及前端 UI 的里程碑）

**产出 `docs/prototype/prototype-vx.y.z-m<n>.html`**——单一 HTML 文件即高保真原型，浏览器直接打开可交互预览：

- 覆盖本里程碑全部界面：布局、交互状态（默认/悬停/加载/空态/错误态）、响应式断点（如适用）
- 界面与 F/AC 的映射关系在 spec 文档中说明，原型本身只承载视觉与交互
- 原型即开发基准：后续实现与原型不一致视为缺陷，除非经我确认变更

⛔ prototype 的 status 为 approved 后才能开始编码。

### 2.3 开发（TDD）

- 严格按 spec 的 Task 顺序执行，不擅自调整顺序和范围。
- **每个功能点按红-绿-重构循环**：
  1. **红**：按测试清单先写单元测试，运行并确认失败——失败原因必须是「功能未实现」，不允许是语法、引用或环境错误
  2. **绿**：写最少实现让测试通过，禁止超前实现测试未要求的功能
  3. **重构**：全绿后清理代码，重构完必须再跑测试确认仍全绿
  4. **收尾**：跑 build / lint → 在 spec 的 Task 表标记完成并附证据（命令 + 结果摘要）→ git commit（测试与实现同一 commit，英文 message，一个 Task 一个 commit）
- **TDD 反作弊**：禁止为让测试通过而改/删断言、写恒真断言、放宽边界条件。确属测试写错，停下说明理由，经我确认后先修测试再继续。
- **Mock 边界**：mock 只用于隔离无关协作者（第三方服务、随机数、时钟），禁止 mock 被测逻辑本身；核心链路不允许纯 mock 覆盖。
- 发现 PRD/spec 缺陷或需新决策：停下来给选项与建议，等我拍板。

### 2.4 里程碑验收（自动化测试）

每个里程碑开发完成后执行，**全部测试自动化，一条命令可跑完**：

- **单元测试**：全量通过（含此前所有里程碑的用例回归）
- **集成测试**（涉及外部系统/外部接口时）：以真实依赖（或等价测试环境）验证对接链路，纯 mock 结果不作为通过依据
- **e2e 测试（真机环境）**：在目标真机/真实运行环境上跑端到端场景，覆盖用户完整操作路径；使用自动化框架（Web 用 Playwright，移动端用 Appium 等），禁止手工点检
- **测试基础设施要求**：提供统一入口命令（如 `npm test` / `npm run test:e2e`），接入 CI 优先；测试失败输出须可定位（失败用例名 + 断言差异 + 日志）
- **验收产出**：在 spec 文档追加「验收记录」章节——测试命令、运行结果、通过率、遗留问题；自测须覆盖边界与异常路径，不只 happy path
- **禁止无证据的「已通过」**。我会抽查复跑，发现一条不不实，本里程碑验收作废重来。

⛔ 验收记录经我确认后，才进入下一里程碑（或进入交付）。

## 阶段三：交付（每个版本一次）

**产出 `docs/release/release-vx.y.z.md`**，章节结构：

1. 版本内容摘要（三句话以内）
2. 变更记录：Added / Changed / Fixed / Removed（只写用户可感知的变化）
3. 交付物清单与获取方式（构建产物、部署说明）
4. 验收汇总：各里程碑验收结论引用、全量测试最终通过率
5. 已知问题与下版建议 backlog

**交付检查单（全部满足才算交付完成）：**

- [ ] 全量自动化测试通过（单元 + 集成 + e2e，含回归）
- [ ] 全部里程碑 spec 的验收记录经我确认
- [ ] release 文档完整且 status 为 approved
- [ ] git 打 tag `vx.y.z`，commit 干净（无未提交变更）
- [ ] 本版全部文档（PRD/spec/prototype/release）整组移入 `docs/archive/vx.y.z/`

交付完成后回到阶段一规划下一版本。

## 贯穿全程：vibe-coding 踩坑记录

**`docs/vibe-coding-log.md`，持续追加，跨版本共用**，记录与业务功能无关、但影响协作效率的坑及解决办法：

- 记录范围：提示词/上下文管理问题、大模型幻觉与诱导偏航、工具链与环境配置坑、代码生成中的反模式、会话中断与续接问题等
- **条目格式**（倒序追加，新的在上）：

```markdown
## 2026-09-28 | <一句话标题>
- 现象：<踩到的坑，什么场景下出现>
- 原因：<根本原因>
- 解决：<具体办法/提示词写法/配置>
- 适用范围：<通用 | 特定工具/框架>
```

- **触发时机**：解决一个坑后立即记录，不攒批；里程碑验收时检查本里程碑期间是否有漏记
- 目的：这些经验跨项目可复用，是 vibe coding 时代最重要的事故库
